# The game port, the sync script, and switching the game to this library

dxWebGL2 was extracted from `Dependencies/WebD3D8` of the Command & Conquer Generals Zero Hour web port
(<https://github.com/scr2em/Generals-Zero-Hours-Web>). This page records what was extracted and changed, how to pull
later changes of the original over (`tools/sync_from_game.sh`), and the exact steps for the game repository to consume
dxWebGL2 instead of its own copy.

## What was extracted

* Source: `Dependencies/WebD3D8` (library `web_d3d8`, ~10 000 lines: `src/`, `include/WebD3D8/WebD3D8.h`, `tests/`) of the
  *committed* version of the game repository, HEAD `1fc50f327a6aaa4e58c66b3872562c5e9b50e084` (the library appears in
  commit `88ad0adfd` "web: Implement Direct3D 8 on WebGL2 (Dependencies/WebD3D8)" and was changed by later snapshots).
  The work that was uncommitted then (context loss, MSAA, more pixel shader ops, diagnostics, performance) was committed
  as `e62d2dae349ec2ef0abafb77616cfb44308d9f12` and has been imported with the sync script (see "Reconciliation" below).
* The raw upstream files of the last import are stored as `tools/sync/upstream_base.tar.xz` (state: `tools/sync/upstream_base.txt`).

## What changed compared with WebD3D8

| Area | Change |
|---|---|
| Name, API | namespace `webd3d8` -> `dxwebgl2`, public header `WebD3D8/WebD3D8.h` -> `dxwebgl2/dxwebgl2.h`, `WebD3D8_*` -> `dxwebgl2_*`, `WEBD3D8_PRESENT_*` -> `DXWEBGL2_PRESENT_*`; **compatibility**: `include/WebD3D8/WebD3D8.h` (macros) and exported `WebD3D8_*` functions (`src/compat/`), both generated by `tools/gen_webd3d8_compat.py`; `dxwebgl2_GetVersionString()` added |
| Structure | flat `src/` split into `src/core` (API independent), `src/api` (COM plumbing) and `src/d3d8` (front end); `GLState` base class of the device (binding caches, caps, read-backs) so that `BufferStorage` and `TextureBase` no longer depend on the Direct3D 8 `Device`; `CreateVertexShaderObject` takes a vertex layout instead of a `D3DVSD_*` declaration; `CreateProgram` lost its unused device argument; `PipelineState::Invalidate` moved to the core. See [ARCHITECTURE.md](ARCHITECTURE.md) |
| Headers | Wine's `d3d8*.h` (patched) and own `d3dx8*.h` instead of the patched Microsoft `min-dx8-sdk`; the Win32/COM base in `dxwebgl2/win32_min.h` instead of the game's WebCompat `windows.h`/`objbase.h`; ABI verified. See [HEADERS.md](HEADERS.md) |
| Build | own CMake project: Emscripten only, install/export + package config, pthread variant, no `-fshort-wchar -fms-extensions -fdeclspec`, no `BUILD_WITH_D3D8` |
| Wide strings | the `W` functions convert UTF-16 to UTF-8 (the original truncated each code unit to `char`); nothing depends on `sizeof(wchar_t)` |
| Bug fixes found by the new tests | `D3DXERR_INVALIDDATA` is `0x88760B59` (the original used the value of another code, `0x88760B54`); `D3DXFresnelTerm` had the ratio of its first term inverted; `D3DXAssembleShaderFromFileW` was declared by the headers but not implemented; `D3DXCreateMatrixStack` was missing (added) |
| License and wording | SPDX headers, "Copyright (C) 2026 dxWebGL2 contributors", game specific remarks (WW3D2, "the game") rephrased generically; the test fixtures that were verbatim copies of the game's inline pixel shaders were replaced by shaders of similar structure (they were Electronic Arts code under the game's additional license terms) |
| Tests | the single picture test now asserts: probe pixels against recorded values, 100+ API expectations, `TEST_RESULT: PASS/FAIL` and an exit code; added the header ABI test, D3DX math, wide strings, project-windows.h integration, WebD3D8 compatibility, examples; see [CONTRIBUTING.md](../CONTRIBUTING.md) |

## Pulling later changes of the game port: `tools/sync_from_game.sh`

> **After the backend split** ([WEBGPU.md](WEBGPU.md), step 1) the GL code of `d3d8/device.cpp`, `d3d8/device_draw.cpp`,
> `d3d8/texture.cpp`, `core/gl_state.*`, `core/program.cpp`, `core/texture_storage.cpp` and `core/buffer_storage.cpp` lives
> in the WebGL2 backend (`src/core/gl/`), and `GLState`/`GLObject` became the backend's state cache and `GpuObject`. The
> rules below still describe the layout of the first sync: upstream changes to those files no longer merge mechanically and
> have to be ported by hand to the front end (state translation) or to `src/core/gl/` (GL calls). Files that the split did
> not touch (the shader translators, the fixed-function generator, formats, D3DX, the diagnostics) sync as before.

```sh
tools/sync_from_game.sh --dry-run          # what would change (does not write)
tools/sync_from_game.sh                    # merge the working tree of the game repository
tools/sync_from_game.sh --source HEAD      # ... or a committed revision (any git revision of the game repository)
tools/sync_from_game.sh --game-repo PATH   # default: $DXWEBGL2_GAME_REPO or /home/user/CnC_Generals_Zero_Hour
```

How it works (`tools/sync/sync_from_game.py`, rules in `tools/sync/sync_rules.py`):

1. The upstream files are read (`Dependencies/WebD3D8` of the game repository).
2. The **same mechanical transformation** that produced this repository is applied to the *last imported* upstream
   files (`tools/sync/upstream_base.tar.xz`) and to the new ones: file mapping (the flat `src/` goes to `core/`, `api/`,
   `d3d8/`; `common.h`, `device.h`, `device.cpp`, `resources.h`, `buffers.cpp`, `texture.cpp`, `vertexformat.cpp` are cut
   at marker lines or function by function), the namespace and symbol renames, include paths, the license header, wording
   rules and a few mechanical edits (the `GLState` base class and the removal of what it provides, shared id counters,
   ...). The edits are *rules*, not hand edits, exactly so that this step reproduces them on new code.
3. For every resulting file, `git merge-file` merges three-way: base = transform(last import), theirs = transform(new
   upstream), ours = the file in this repository. Hand edits made here survive; overlapping edits get conflict markers.
4. New upstream files are placed by the mapping (`diag.*`, `glcount.h` go to `src/core`, other new `src/*` files to
   `src/d3d8` with a warning, tests to `tests/runner` with a warning), files deleted upstream are only reported.
5. After a merge **without conflicts** the new upstream state is recorded as the base for the next run. With conflicts it
   is not: resolve them, build, run `scripts/test.sh`, then run `tools/sync_from_game.sh --record-base`.
6. `tools/gen_webd3d8_compat.py` regenerates the `WebD3D8` compatibility files from the public header.

Output: lists of new, merged and conflicting files, and warnings:

* `... game specific wording left: ...`: new upstream text with game vocabulary; rephrase it (and add a rule to
  `WORDING` if the same text will keep coming back).
* `... expected text not found (...)`: upstream changed text that a mechanical edit relies on (the
  `Device`/`GLState` split); reconcile by hand as described below.
* `... has no mapping ...`: a new upstream file; check its placement (`src/core` if it is API independent).
* `marker not found: ...` (an error): upstream moved a landmark that the splitting uses; adjust `sync_rules.py`.

### Reconciliation of the first sync (game revision `e62d2dae3`)

The first import was HEAD `1fc50f327`. The work that was in flight in the game repository then (context loss and restore,
multisampling, the remaining pixel shader instructions, diagnostics, performance caches, the feature tests) was committed as
`e62d2dae3` ("web: Complete Direct3D 8 on WebGL2 ...") and brought over with `tools/sync_from_game.sh --source HEAD`: 23
files merged without conflicts, 7 new files placed by the mapping. What the merge could not decide by itself was resolved
**in the rules** (so the next sync reproduces it), because it was all of one kind: upstream code that assumed that the
device class holds GL state which the resource classes now get from `GLState`.

1. `GLObject` (the registry of everything that owns WebGL names, for context restoration) takes a `GLState *`;
   `RegisterGL` / `UnregisterGL`, the list head `m_glObjects` and the new `NotifyContextLost()` / `NotifyContextRestored()`
   live in `GLState` (`core/gl_state.cpp`; the device calls the two notify functions where upstream iterated the list).
2. `GLState::BindBuffer / ForgetBuffer / ForgetTexture / ReadTextureLevel` keep the cache logic in the core and reach what
   only the front end has (the element array binding of the bound vertex array object, framebuffer attachment keys, the
   vertex array cache, the multisampled back buffer) through virtual hooks: `BufferBindingSlot`, `OnForgetTexture`,
   `OnForgetBuffer`, `PrepareTextureRead`. The device implements them (`d3d8/device.h`, end of `d3d8/device.cpp`); the bodies
   are cut out of the upstream functions by the rules, not rewritten. Upstream's `Device::BindBuffer` is removed (otherwise
   there would be two caches).
3. `diag.cpp`, `diag.h`, `glcount.h` went to `src/core`; the Direct3D level counters in `diag.h` are plain integers, so the
   layering check (`tools/check_layering.py`) is fine with them.
4. The feature test was moved to `tests/runtime/d3d8_features_test.cpp` with `tests/runner/run_features.mjs`; the cases that
   loaded the game's shader files (EA code) use inline shader sources of similar structure instead (a rule replaces
   `ReadShaderFile`), and the cases are named `inline_shaders` / `inline_vshaders`. `run_regression.mjs` and
   `reference_hashes.json` are placed in `tests/runner`. Upstream's `COVERAGE.md` (with a game-use column) is not mapped; its
   implementation statuses were merged into `docs/COVERAGE.md` by hand. If a later upstream sync changes `COVERAGE.md`,
   the script reports it as "ignored".

Things to look at after any sync: `... expected text not found (...)` warnings (a rule that no longer matches), the
`game specific wording` warnings, `tests/runner/reference_hashes.json` (a changed rendering changes the hashes; review the
pictures before `run_regression.mjs --update`).

The file `tests/runtime/expected_probes.inc` may need re-recording after intended rendering changes
(`node tests/runner/record_probes.mjs build/tests`).

## Switching the game repository to dxWebGL2

The steps, in the game repository:

1. **Add the dependency** in `cmake/emscripten.cmake`, replacing the `dx8` FetchContent block with its patch and
   `add_subdirectory(Dependencies/WebD3D8)`:

   ```cmake
   include(FetchContent)
   # Direct3D 8 on WebGL2 and the Direct3D 8 / D3DX 8 headers.
   FetchContent_Declare(dxwebgl2
       GIT_REPOSITORY https://github.com/scr2em/dxWebGL2.git
       GIT_TAG        <commit or tag>
       EXCLUDE_FROM_ALL)
   set(DXWEBGL2_BUILD_TESTS OFF CACHE BOOL "" FORCE)
   set(DXWEBGL2_BUILD_EXAMPLES OFF CACHE BOOL "" FORCE)
   set(DXWEBGL2_INSTALL OFF CACHE BOOL "" FORCE)
   set(DXWEBGL2_BUILD_PTHREADS ON CACHE BOOL "" FORCE)             # the game links with -pthread / PROXY_TO_PTHREAD
   set(DXWEBGL2_USE_PROJECT_WINDOWS_H ON CACHE BOOL "" FORCE)      # use WebCompat's windows.h / objbase.h ...
   set(DXWEBGL2_WINDOWS_H_TARGET deps_config CACHE STRING "" FORCE) # ... and its flags (-fshort-wchar), see below
   FetchContent_MakeAvailable(dxwebgl2)
   ```

   `deps_config` is the interface target that already carries the WebCompat include directory (through
   `webcompat_headers`) and the compile flags (`-fshort-wchar` ...); dxWebGL2 then compiles with the same `WCHAR` as the
   game. The global `CMAKE_CXX_FLAGS` set at the top of `cmake/emscripten.cmake` (`-pthread`, `-fwasm-exceptions`) apply to
   the fetched project as well.

2. **Keep the rest of the SDK, behind dxWebGL2's headers**: `dinput.h`, `ddraw.h` (DDS constants), `dsound.h` and
   friends still come from the `min-dx8-sdk` checkout, but the checkout is no longer patched and no longer ahead of
   dxWebGL2 on the include path:

   ```cmake
   FetchContent_Declare(dx8 GIT_REPOSITORY https://github.com/TheSuperHackers/min-dx8-sdk.git
                            GIT_TAG 7bddff8c01f5fb931c3cb73d4aa8e66d303d97bc)   # without PATCH_COMMAND
   FetchContent_GetProperties(dx8)
   if(NOT dx8_POPULATED)
       FetchContent_Populate(dx8)
   endif()
   add_library(d3d8lib INTERFACE)
   target_compile_definitions(d3d8lib INTERFACE BUILD_WITH_D3D8)
   # Only after the system and dxWebGL2 headers: <d3d8.h>/<d3dx8.h> must be dxWebGL2's.
   target_compile_options(d3d8lib INTERFACE "SHELL:-idirafter ${dx8_SOURCE_DIR}" "SHELL:-idirafter ${dx8_SOURCE_DIR}/extra")
   target_link_libraries(d3d8lib INTERFACE dxWebGL2::dxwebgl2_pthreads)
   ```

   (Delete `cmake/patches/dx8-emscripten.patch` and the `PATCH_COMMAND` of `dx8`; the gamespy patch stays.) If a source
   file includes an SDK header that dxWebGL2 also provides *and* needs the Microsoft one, it is not possible any more; the
   web build never needs it.

3. **Source changes** (all optional thanks to the compatibility layer, recommended):
   * `GeneralsMD/Code/Main/WebMain.cpp`: `#include <WebD3D8/WebD3D8.h>` keeps working (macros); change it to
     `#include <dxwebgl2/dxwebgl2.h>` and rename `WebD3D8_*` -> `dxwebgl2_*`, `WEBD3D8_PRESENT_*` -> `DXWEBGL2_PRESENT_*`,
     `WebD3D8_PlatformHooks` -> `dxwebgl2_PlatformHooks` (a `sed` does it).
   * `Dependencies/WebCompat/src/win32_misc.cpp` declares `extern "C" void *WebD3D8_LookupProc(const char *) __attribute__((weak))`
     itself: it keeps working (the library exports the old name and always links it), rename it to `dxwebgl2_LookupProc`
     when convenient.
   * Command line options (the page URL's `?arg=`) are renamed: `-webd3d8report[=s]` -> `-dxwebgl2-report[=s]`,
     `-webd3d8shaders` -> `-dxwebgl2-shaders`, `-webd3d8loseafter=N[,M]` -> `-dxwebgl2-loseafter=N[,M]`,
     `-webd3d8debug` -> `-dxwebgl2-debug`; scripts of the game that pass the old ones (for example
     `GeneralsMD/Code/Main/web/test/starter_flow.mjs`) need the same rename.

4. **Delete `Dependencies/WebD3D8`** (including its tests) and run the game build and its tests. The library's own tests
   now live in dxWebGL2 (`scripts/test.sh`).

5. For development against a local checkout use `-DFETCHCONTENT_SOURCE_DIR_DXWEBGL2=/path/to/dxWebGL2` instead of a Git tag.

## What was checked for the game

The following was verified before the extraction was handed over (see the report of the extraction for the numbers):

* The game's Win32 compatibility headers (`Dependencies/WebCompat/include`, with `-fshort-wchar -fms-extensions
  -fdeclspec` like the game's compile line) together with dxWebGL2's headers: no redefinition, and all 1080 ABI
  assertions of `tests/data/d3d8_abi_expected.inc` hold (detection through the include guard and through the explicit
  define).
* A program built that way links against the library (built *without* `-fshort-wchar`), calls `Direct3DCreate8`, D3DX
  and the old `WebD3D8_*` names, and runs.
* The game's own sources that include the Direct3D headers (the WW3D2 library, W3DDevice, ...) were compiled (syntax
  only, the same command lines as in the game's build with the `min-dx8-sdk` directory replaced by dxWebGL2's headers, the
  `min-dx8-sdk` checkout behind them for `dinput.h` and friends): 951 of 965 translation units compile. The 14 others do
  not touch Direct3D: stale entries of the game's compile database (a file that no longer exists, a test built with
  `-std=c++98`, which dxWebGL2's headers do not support), the `EABrowserDispatch` header missing from the checkout (6
  web browser files) and the in-flux pathfinder sources (5 files).
